Tutorial

Build a study-ready VA on MIVAIS

From an empty folder to a working mixed-initiative visual analytics system — and from there to a controlled, replayable user study — in twelve steps.

~30 minutes · Python + a little vanilla JavaScript · the finished system ships in this repository as Starter_VA/ · five full showcase studies live in studio/studies/

What's ahead
  1. Part 1 — Build the VA: one config file, one agent, the wiring, one HTML file. With live demos.
  2. Part 2 — Study it: describe a study in YAML, upload & register it, run it, replay it.
  3. Part 3 — Bring your own interface: the exact contract to adapt, and where to go next.

What you will build

The Starter VA: a scatterplot of 24 classic cars where the analyst picks the x- and y-axis attributes — and an InsightAgent that watches those choices and, unprompted, computes the correlation and comments on it in the shared chat.

analyst changes an axis → agent observes → agent writes an insight → everyone sees it

That loop is mixed-initiative visual analytics in miniature. The point of building it on MIVAIS is what you don't write: permissions, audit logging, real-time synchronization across clients, chat, presence, and a replayable session recording all come from the infrastructure. Your code is the scatterplot and the agent — about 200 lines of application logic, total.

Three ideas carry everything:

  • World State — a shared key-value blackboard. Humans and agents never call each other; they read and write keys.
  • Capabilities — one config file declares who may read/write which keys and publish on which topics. Humans and agents are declared in the same vocabulary.
  • Watch — an agent registers a callback on a key and becomes part of the loop. Nobody invokes it.
Live demo — a full-scale system built on the same seven components

This is the hosted PODIUM — a published mixed-initiative ranking system reimplemented on MIVAIS. Drag a car, nudge a weight, and watch the ranking agent react. Everything you build in this tutorial uses exactly the same infrastructure.

Part 1 — Build the VA

1Project layout & install

MIVAIS is a plain Python package in this repository — clone the repository first; there is nothing to install from a package index. You need Python 3.11+ and Node only if you later want a build-step frontend (the Starter VA needs none). Create the folders and install MIVAIS editably next to your app:

Starter_VA/
├── backend/
│   ├── main.py               # all wiring (steps 4–5)
│   ├── agents_config.yaml    # who may do what (step 2)
│   ├── agents/insight_agent.py   # the one agent (step 3)
│   └── requirements.txt      #   -e file:../../MIVAIS  +  fastapi, uvicorn
└── frontend/
    └── index.html            # one file, no build step (step 6)

$ cd Starter_VA/backend
$ pip install -r requirements.txt

2Declare who may do what

Everything the infrastructure enforces at runtime is declared here — for the two human roles and the agent, in identical terms. Note the asymmetry that guides you while developing: an empty can_write means write nothing (fail-closed), an empty can_read means read everything.

backend/agents_config.yaml 
{
  "users": [
    { "role": "analyst",
      "can_read": [], "can_write": ["selected_attributes"],
      "bus_publish_topics": ["chat.message"],
      "bus_subscribe_topics": ["chat.message"] },
    { "role": "observer",
      "can_read": [], "can_write": [],
      "bus_publish_topics": [],
      "bus_subscribe_topics": ["chat.message"] }
  ],
  "agents": [
    { "agent_id": "insight_agent", "class": "InsightAgent", "enabled": true,
      "can_read": ["dataset", "selected_attributes"],
      "can_write": ["insight"],
      "bus_publish_topics": ["chat.message"], "bus_subscribe_topics": [],
      "params": { "strong_threshold": 0.7, "moderate_threshold": 0.4 } }
  ]
}

Want a third role, or a stricter agent? Edit this file. No application code changes.

3Write the agent

An agent subclasses BaseAgent and implements one coroutine: run(). It reaches the world only through four inherited helpers — self._read, self._write, self._publish, self._subscribe — which bind the agent's identity into every call, so everything it does is permission-checked and audit-logged as insight_agent.

backend/agents/insight_agent.py 
class InsightAgent(BaseAgent):

    async def run(self):
        # become part of the loop: react whenever ANYONE changes the selection
        self._ws.watch("selected_attributes", self._on_selection)
        sel = self._read("selected_attributes")
        if sel: await self._analyze(sel)          # comment on the initial view too
        await asyncio.Event().wait()              # all further work is watch-driven

    async def _on_selection(self, key, value):
        await self._analyze(value)

    async def _analyze(self, sel):
        data = self._read("dataset", [])
        r = pearson([row[sel["x"]] for row in data],
                    [row[sel["y"]] for row in data])
        strength = ("strong" if abs(r) >= self.params["strong_threshold"] else
                    "moderate" if abs(r) >= self.params["moderate_threshold"] else "weak")
        self._write("insight", { "x": sel["x"], "y": sel["y"], "r": round(r, 3),
                                 "strength": strength, "text": "…" })
        await self._publish("chat.message", {
            "from": self.agent_id, "to": "broadcast",
            "text": f"Looking at {sel['x']} vs {sel['y']}: {strength} correlation (r = {r:+.2f})." })

That's the whole pattern: watch → read → compute → write / publish. The full file (with the pure-Python pearson) is Starter_VA/backend/agents/insight_agent.py.

4Wire the infrastructure

Seven components, constructed once, in dependency order. This block is the same in every MIVAIS application — PODIUM, Voyager 2 and ProactiveVA in this repository wire the exact same seven lines. (_user_configs is simply the users list from step 2, keyed by role.)

backend/main.py 
audit_log   = AuditLog()
registry    = AgentRegistry()
guard       = PermissionGuard(registry)
world_state = WorldState(audit_log=audit_log, permission_guard=guard)
bus         = MessageBus(audit_log=audit_log)
recorder    = SessionRecorder(RECORDINGS_DIR)

class StarterGateway(Gateway):
    # ONE override: translate your domain action into a state write. The write
    # is attributed to the connected user and checked against their role.
    async def _handle_action(self, agent_id, session_id, data):
        if data.get("action") == "select_attributes":
            self._ws.write(agent_id, "selected_attributes",
                           {"x": data["x"], "y": data["y"]}, event_type="user_action")

gateway = StarterGateway(world_state=world_state, audit_log=audit_log,
                         registry=registry, bus=bus,
                         user_configs=_user_configs, recorder=recorder)

At startup, register each configured agent and seed the state (system_write is the one startup-only bypass of the guard):

for cfg in _config["agents"]:
    cap = AgentCapabilities(agent_id=cfg["agent_id"], can_read=cfg["can_read"],
                            can_write=cfg["can_write"],
                            bus_publish_topics=cfg["bus_publish_topics"], ...)
    instance = _AGENT_CLASSES[cfg["class"]](agent_id=cap.agent_id,
                world_state=world_state, message_bus=bus, params=cfg["params"])
    registry.register(cap, instance)
    asyncio.create_task(instance.run())

world_state.system_write("dataset", DATASET)
world_state.system_write("selected_attributes", {"x": "horsepower", "y": "mpg"})

5Expose the three endpoints

Every MIVAIS VA serves exactly three things: its frontend, a WebSocket, and a health/state probe.

@app.get("/")                       # the frontend
async def index():
    return FileResponse(HERE.parent / "frontend" / "index.html")

@app.websocket("/ws/{session_id}")  # the real-time channel — Gateway does the rest
async def ws_endpoint(ws, session_id, role: str = "analyst"):
    await gateway.connect(session_id, ws, role=role)
    try:
        while True:
            await gateway.receive_and_apply(session_id, await ws.receive_text())
    except WebSocketDisconnect:
        pass
    finally:
        await gateway.disconnect(session_id)

@app.get("/state")                  # health check + snapshot
async def state():
    return {"ok": True, "world_state": world_state.snapshot()}

6The frontend — one file, three message types

No framework required (the Starter VA is a single static HTML file — though nothing stops you from using React, Vue or Svelte: the contract is just a WebSocket). The browser speaks a three-message protocol with the Gateway:

directionmessagemeaning
receive{type:"initial_state", world_state, my_permissions, chat_history} full snapshot on connect + what this role may do (drive your UI's enabled/disabled state from it)
receive{type:"state_update", world_state, connected_users} pushed after every accepted write, whoever made it — just re-render
receive{type:"bus_message", message:{topic, payload}} chat and other subscribed topics
send{action:"select_attributes", x, y} your domain actions (handled by your _handle_action)
send{action:"chat_message", text, to:"broadcast"} built-in — chat, cursors, drag are free
const ws = new WebSocket(`ws://${location.host}/ws/${uid}?role=${role}`);
ws.onmessage = (ev) => {
  const msg = JSON.parse(ev.data);
  if (msg.type === "initial_state" || msg.type === "state_update") {
    state = Object.assign(state, msg.world_state);
    render();                              // one render function, state-driven
  }
  if (msg.type === "bus_message") addChat(msg.message.payload);
};
selX.onchange = () => ws.send(JSON.stringify(
    { action: "select_attributes", x: selX.value, y: selY.value }));

Run it and open two tabs — one of them with ?role=observer — to watch the synchronization and the permission asymmetry:

$ python main.py          →  http://127.0.0.1:7300
Checkpoint. Change an axis in one tab: the plot updates in both, the agent's comment appears in the chat, and the observer tab's dropdowns are disabled — that is the role config from step 2, enforced by the Permission Guard, reflected by my_permissions. A JSONL recording of everything is already being written to backend/recordings/.

Part 2 — Study it in Studio

Because the recording, the audit trail and the state broadcasts already exist, the Session Tracking Tool (this application) can run a controlled study on your VA without you adding anything to it. You describe the study declaratively; Studio spawns or embeds your VA, observes it, and records one timeline per session. The admin you are using is a React SPA over a plain REST API (/api/…) — every click below has a documented endpoint behind it.

7Describe the study

A study is a directory of YAML files. The va: block tells Studio how to run your system — one private instance per session:

studio/studies/starter-tutorial/study.yaml 
id: starter-tutorial
name: "Starter VA — tutorial study"
mode: singleplayer

va:
  system: starter
  spawn_cmd: "python main.py"          # {port}/{recording_dir} placeholders available
  cwd: "../Starter_VA/backend"
  iframe_url: "http://127.0.0.1:{port}/"
  health_check_url: "http://127.0.0.1:{port}/state"

blocks:
  - id: intro
    tasks: [welcome]
  - id: main
    tasks: [explore, question]
  - id: outro
    tasks: [thanks]

The spawn contract is two environment variables. Studio sets STUDIO_VA_PORT (a free port) and STUDIO_VA_RECORDING_DIR (where to write the JSONL); the Starter VA honours both in four lines at the top of main.py. Studio probes health_check_url, mounts iframe_url beside the task, and tails the recording directory — that tail is the study's event stream.

8Define the tasks

Tasks live one per file, one type per question. The full toolbox: info_screen, single_choice, multi_choice, likert, slider, number_input, free_text, and va_interaction — plus ground truths (exact / set / ordered / regex), timers, optional tasks, and conditional flow (next: rules that branch, skip or drop). The interesting one embeds your VA, resets it to a defined baseline, requires a detectable action, and captures part of the shared state as the answer:

studio/studies/starter-tutorial/tasks/explore.yaml 
id: explore
type: va_interaction
prompt_md: |
  ## Find a strongly related attribute pair
timer_seconds: 180

world_state:                    # same start state for every participant,
  mode: replace                 # pushed through the Gateway — no VA support needed
  initial:
    selected_attributes: { x: horsepower, y: mpg }
    insight: null

task_steps:
  - id: change-axes
    label: "Change an axis attribute"
    mode: auto                  # only a real VA action ticks it — the checkbox
    auto_check_on:              # is read-only and manual ticks are rejected
      event_type: user_action
      meta: { action: select_attributes }

answer:
  type: capture_state           # the analytical state IS the answer
  world_state_key: selected_attributes

A follow-up question with one of the newer tools, kept beside the running VA:

id: confidence
type: slider                    # also available: number_input
with_va: true                   # keep the VA visible while answering
prompt_md: "## How confident are you in what you found?"
min: 0
max: 100
step: 5
unit: "%"
min_label: "Not at all"
max_label: "Completely"

9Register & run

  • Log into the admin at /admin/login — the credentials come from the STUDIO_ADMIN_USERNAME / STUDIO_ADMIN_PASSWORD environment variables (admin / change-me in the local docker-compose defaults).
  • In the admin, go to Register a study. Two paths:
    • Upload your study.yaml straight from that page — it is validated against the typed schema and registered in one step. The individual tasks are still read from the study directory's tasks/ folder, and a missing task file produces a precise error naming it.
    • Or drop the whole directory under studies/ and register it from the on-disk list.
  • On the study page, + New code mints an access code; open the join link in a private window. For a multiplayer study, + Mint cohort creates one code per declared role, all bound to the same lobby — hand one link to each participant and the session starts when everyone is ready.
  • Walk through it: consent → welcome → the scatterplot task (watch the checklist tick itself when you change an axis) → question → done.
  • Want a ping when someone finishes? System → Webhooks: register a signed JSON endpoint of your own, or paste a Discord webhook URL and pick the participant_finished event — no receiving code needed.

10Watch it live, then replay it

While the session runs, the live view shows lobby state, per-participant progress and a manual advance control for operator-paced designs. Afterwards, open the session and hit Replay: one scrubbable timeline (the recording itself has no separate scrubber — the study timeline drives everything) with a lane for every participant and a lane for every software agent, the study's own lifecycle, synced screen recordings with a POV switcher — a camera icon marks whose eyes you are looking through, and the transcript follows the selected participant — markers and shared notes for qualitative coding. Exports (CSV / Parquet / frozen preregistration JSON) are on the study page.

That's the whole loop. You never instrumented the Starter VA for any of this. The same recording that let you replay your dev session is what Studio analyzes — reused, not added.

Part 3 — Bring your own interface

The Starter VA is a template. To put your visualization in its place, map your application onto the same four seams:

your system has…express it as…
application state (selections, filters, results, notes) World State keys — one key per independently-updated thing; agents and the UI re-render from state_update
user interactions {action: "…"} messages, translated into writes in your Gateway subclass's _handle_action
automated logic (stats, ML, an LLM) agents: watch the triggering keys, compute, _write / _publish the result — see the three PODIUM agents and the LLM-driven ProactiveVA agents in this repo for rule-based, ML and ReAct-style examples
user types / conditions roles in agents_config.yaml — permissions only, never if role == … in code

Keep this contract and Studio needs nothing else from you:

  • Endpoints: / (UI), /ws/{session_id}?role=…, /state (health).
  • Spawn: honour STUDIO_VA_PORT and STUDIO_VA_RECORDING_DIR; keep the SessionRecorder on.
  • Hosted instead of spawned? If your VA runs as one shared deployment, set external: true + your URL in the study YAML, and relay events from your frontend so Studio can still observe the session: 
    window.parent.postMessage({ source: "mivais-va", kind: "va_event",
  event: { type: "user_action", action: "select_attributes", data: {...} } }, "*");
    A shared deployment must also isolate concurrent sessions — see the room-per-session pattern in PODIUM_V2/backend/main.py (Studio appends ?room=<session id> automatically). Extra URL params pass straight through and let one deployment serve many study configurations — the hosted Voyager, for example, picks its dataset per room from ?dataset=<name> in the study's iframe_url.
  • Big data? Exclude bulky keys from broadcasts (_broadcast_exclude_keys) and ship them once in initial_state, as PODIUM does with its dataset.
  • Think-aloud? Flip the study's recording: block to video: screen + transcribe: true — screen, audio and a time-aligned transcript appear in the replay with no VA changes.

12Analyze beyond a single session

Everything a study produces is queryable from the admin: per-task summaries and drill-downs, the participant funnel, Compare studies for cross-condition aggregates, and IRR (κ) for the reliability of qualitative codes two reviewers attach during replay. Data leaves via CSV / Parquet exports and a frozen, hash-stamped copy of the study definition for preregistration.
